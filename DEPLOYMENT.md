# Production Deployment Guide

## Prerequisites

- Render account (render.com)
- Supabase production project (separate from dev)
- Resend account for emails (resend.com)
- GitHub repository connected to Render
- Supabase CLI logged in, for the migration step

---

## 1. Supabase Production Project

1. supabase.com → New Project
2. Name: `portfolio-prod`
3. Same region as the Render service (see `render.yaml`)
4. Save the **Database password** securely
5. Wait for the project to be ready

### Connection string

Settings → Database → Connection string → **Session pooler** (port `5432`),
not the direct connection. Render opens a new connection per deploy and the
transient pool can exceed Supabase's direct-connection limit under it; the
session pooler is what that connection string is meant for. Build the URL as:

```
postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

`src/lib/db/client.ts` already passes `prepare: false` to `postgres`, which is
what a pooler needs.

**Supabase API keys** (Settings → API):

| Value | Purpose |
|-------|---------|
| Project URL | `SUPABASE_URL` |
| `service_role` (secret) | `SUPABASE_SERVICE_ROLE_KEY` |

**Storage buckets** (Storage → New bucket), matching the constants in
`src/lib/storage/index.ts`:

| Bucket | Public |
|--------|--------|
| `cv-images` | ON |
| `cv-files` | OFF |

## 2. Resend (Emails)

1. resend.com → API Keys → Create API Key
2. Add and verify your sending domain (recommended)
3. Copy the API key → `RESEND_API_KEY`
4. Set `CONTACT_NOTIFY_EMAIL` to the inbox that should receive submissions

## 3. Deploy to Render

1. Render dashboard → **New → Blueprint**
2. Connect the GitHub repo `PeterIregi/piregi-portfolio`, branch `main`
3. Render reads `render.yaml` and shows the service with fields prefilled.
   The six `sync: false` values are prompted for here:
   - `NEXT_PUBLIC_SITE_URL` — the public origin, scheme included. Use your
     custom domain if you have one; otherwise the
     `https://piregi-portfolio.onrender.com` host Render assigns, which you
     can only know after the first deploy (see step 6).
   - `DATABASE_URL`
   - `SUPABASE_URL`
   - `SUPABASE_SERVICE_ROLE_KEY`
   - `RESEND_API_KEY`
   - `CONTACT_NOTIFY_EMAIL`
4. `AUTH_SECRET` is generated by the blueprint (`generateValue`). Read it
   afterwards from the service's Environment tab if you need the same value
   in CI.
5. **Apply** → wait for the build

`AUTH_TRUST_HOST=true` is set in the blueprint and is required on Render.
Auth.js trusts the `Host` header only when that flag is set or when it
recognises the host platform; Vercel sets `VERCEL=1` and Render sets nothing
Auth.js knows about, so without it every `/api/auth/*` request fails with
`UntrustedHost` and the admin login form looks broken.

### Auto-deploy

`render.yaml` sets `autoDeploy: true`, so Render deploys every push to
`main`. CI (`.github/workflows/ci.yml`) runs the lint, typecheck, and token
checks on the same pushes; the workflow only builds, it does not deploy.

---

## 4. Custom Domain

1. Render → your service → Settings → Custom Domains → Add
2. Add the domain to your DNS provider as instructed
3. Render provisions the TLS certificate automatically
4. Update `NEXT_PUBLIC_SITE_URL` to the custom origin and redeploy

Once the domain is live, update `NEXT_PUBLIC_SITE_URL` away from the
`onrender.com` host. Sitemap, robots, JSON-LD, and Open Graph tags all read it
via `src/lib/site-url.ts`; a stale value points search engines and social
previews at the wrong origin.

## 5. Run Migrations and Seed

`render.yaml` sets `preDeployCommand: pnpm db:migrate`, which runs on every
deploy on a paid plan and aborts the release if it fails. Two cases it does
not cover:

**Migrations on the free plan** (no pre-deploy command): either paste
`pnpm db:migrate` into the service's Shell tab, or run it from your machine:

```bash
DATABASE_URL="postgresql://..." pnpm db:migrate
```

**Seeding.** The public pages are built against seed data (design.md §10), so
a fresh production database needs it before the site shows anything:

```bash
DATABASE_URL="postgresql://..." \
SUPABASE_URL="..." \
SUPABASE_SERVICE_ROLE_KEY="..." \
pnpm db:seed
```

The seed inserts fixed uuids with `onConflictDoNothing`, so it is safe to
re-run. It also uploads images to the `cv-images` bucket, which is why it
needs the Supabase vars and not just `DATABASE_URL`.

### Verify the schema actually applied

`pnpm db:check` is not optional. A production database created before the
constraint lines were added to migration 0000 applies that file without
picking them up, and `db:generate` cannot detect this: it compares
`schema.ts` against the snapshots, not the snapshots against your database.
`db:check` compares the live catalog against the migration files and fails on
anything missing, which is the only way to notice before a `NOT NULL` or a
foreign key silently isn't there (#60).

```bash
DATABASE_URL="postgresql://..." pnpm db:check
```

## Rollback

Render → your service → Events → pick an earlier successful deploy →
**Rollback**. This redeploys that commit; it does not revert the database, so
a deploy that included a migration is not undone by rolling back the code.

---

- Resend → Logs

## Security Checklist

- [ ] `AUTH_SECRET` is unique, 32+ chars (blueprint generates one)
- [ ] `AUTH_TRUST_HOST=true` set, or admin login 500s
- [ ] `SUPABASE_SERVICE_ROLE_KEY` only in server env, never client
- [ ] `RESEND_API_KEY` restricted to the sending domain
- [ ] `NEXT_PUBLIC_SITE_URL` matches the domain actually served
- [ ] Admin password changed from the seeded default
- [ ] TLS active on the custom domain
- [ ] Health check green on `healthCheckPath: /`
